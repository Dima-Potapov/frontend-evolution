# 03 — Лента постов в ООП-стиле (классы ES6, модули)

> Третья ступень «эволюции фронтенда». Снова тот же чистый JavaScript, что и в `01-vanilla-js`, без jQuery. Но код **организован по-другому**: он разбит на классы и модули, у каждого из которых одна обязанность. Это мост между «скриптом на странице» и компонентами Vue/React.

---

## Что делает приложение

Функции прежние: добавить пост (заголовок + текст), лайкнуть (+1), удалить с подтверждением `confirm`, показать «Постов пока нет», когда список пуст. Подзаголовок теперь **фиолетовый**, по нему видно, что открыта третья версия.

---

## Как запустить (важно!)

В этой версии используются **ES-модули** (`<script type="module">`, `import` / `export`). Если открыть `index.html` двойным кликом (адрес `file://...`), браузер заблокирует загрузку модулей по политике CORS, и страница не заработает. Нужен локальный сервер. Подойдёт любой из вариантов:

- **VS Code**: расширение *Live Server*, затем правый клик по `index.html` → *Open with Live Server*;
- **Node.js**: в папке `03-oop` выполнить `npx serve .`;
- **Python**: в папке `03-oop` выполнить `python -m http.server 8000` и открыть `http://localhost:8000`.

Интернет больше не нужен: внешних библиотек нет.

## Почему вообще понадобилось что-то менять

Версии 01 и 02 работают, и для 50 строк кода они вполне хороши. Но представьте, что в приложение добавили комментарии, авторизацию, фильтры и загрузку с сервера. В одном файле окажутся перемешаны:

- **данные** (массив `posts`, счётчик id);
- **логика** (как поставить лайк, что считать некорректным постом);
- **отображение** (создание карточек, работа с DOM);
- **обработка событий** (клики, отправка формы).

Любая правка задевает всё сразу. В одном месте забыли вызвать `render()`, и экран разошёлся с данными. Кто угодно может написать `posts = 42` из любой точки файла. Такой код называют «спагетти».

ООП предлагает разложить ответственность по «ящикам» (классам) так, чтобы каждый знал только своё.

## ООП за 3 минуты

**Класс** — это чертёж, **объект** (экземпляр) — изделие по чертежу: `new Post('Заголовок', 'Текст')`.

#### Инкапсуляция — «спрячь внутренности»
Приватные поля `#posts`, `#likes`, `#id` недоступны снаружи класса. Написать `post.#likes = 1000` нельзя: будет `SyntaxError` ещё до запуска. Изменить лайки можно только через метод `like()`. Класс сам охраняет свои правила (например, «лайков не бывает меньше нуля», «пост без заголовка не создаётся»).

#### Наследование — «возьми готовое и расширь»
`class PostStore extends EventEmitter`: хранилище **умеет всё, что умеет EventEmitter** (`on`, `emit`), и добавляет своё (`add`, `like`, `remove`). Если у наследника есть свой `constructor`, в нём обязательно нужно вызвать `super()` до обращения к `this`. У `PostStore` своего конструктора нет, поэтому JavaScript подставляет конструктор по умолчанию, который вызывает `super()` сам.

#### Полиморфизм — «один интерфейс, разные реализации»
`App` не важно, *какой именно* объект передан как `postView`. Главное, чтобы у него были методы `render`, `onLike`, `onDelete`. Можно написать `TablePostView` или `ConsolePostView` с теми же методами, и `App` будет работать без изменений.

#### Под капотом: классы — это «сахар» над прототипами
`class` появился в ES2015 (ES6), но новой модели объектов не принёс. Методы класса лежат в `Post.prototype`, а у каждого экземпляра есть скрытая ссылка `[[Prototype]]` на него. Поэтому 1000 постов не хранят 1000 копий метода `like`: метод один на всех. Проверьте в консоли: `Object.getPrototypeOf(post) === Post.prototype` → `true`, `typeof Post` → `'function'`.

## Карта файлов и архитектура

```
03-oop/
├── index.html            ← разметка, подключает только js/main.js как модуль
├── style.css             ← стили (как в v2, только фиолетовый подзаголовок)
└── js/
    ├── EventEmitter.js   ← «рация»: подписка (on) и оповещение (emit)
    ├── Post.js           ← МОДЕЛЬ одного поста: данные + правила
    ├── PostStore.js      ← МОДЕЛЬ списка: хранит посты, кричит 'change'
    ├── PostView.js       ← ПРЕДСТАВЛЕНИЕ списка: рисует карточки, ловит клики
    ├── PostFormView.js   ← ПРЕДСТАВЛЕНИЕ формы: отдаёт {title, body}
    ├── App.js            ← КОНТРОЛЛЕР: соединяет модель и представления
    └── main.js           ← ТОЧКА ВХОДА: создаёт объекты и запускает App
```

Это классическая схема **MVC** (Model — View — Controller):

```
   пользователь кликает «❤️»
            │
            ▼
   PostView.onLike(id) ──────► App ──────► store.like(id)
                                              │
                                   post.like() + emit('change')
                                              │
   PostView.render(posts) ◄──── App ◄─────────┘
            │
            ▼
       экран обновлён
```

Обратите внимание: **данные текут по кругу в одну сторону**. View никогда не меняет данные сам, он только сообщает о намерении. Модель никогда не трогает DOM. Ровно эта идея (однонаправленный поток данных) станет фундаментом React, Redux и Zustand.

#### Паттерн «Наблюдатель» (Observer)
`EventEmitter` — самая важная деталь версии. `store.on('change', callback)` означает: «когда данные изменятся, позови меня». Именно поэтому в `PostStore` нигде нет вызова `render()`: хранилище даже не знает, что его кто-то рисует. В v1/v2 мы вызывали `render()` вручную после каждого действия, а теперь перерисовка происходит автоматически по событию.

То же самое под капотом делают:
- **Vue**: реактивные объекты (`ref`, `reactive`) сами «эмитят» изменения, и шаблон перерисовывается;
- **React**: `setState` / `useState` сообщает React «состояние изменилось, перерендерь»;
- **Zustand**: `useStore` — подписка компонента на хранилище, почти как наш `store.on('change')`;
- **Node.js**: встроенный класс `EventEmitter` с теми же методами `on` / `emit`.

## Сравнение трёх версий

| Аспект | v1 Vanilla JS | v2 jQuery | v3 ООП |
|---|---|---|---|
| Файлы JS | 1 (`main.js`) | 1 (`main.js`) + jQuery с CDN | 7 модулей |
| Подключение | обычный `<script>` | 2 обычных `<script>` | `<script type="module">` |
| Где хранятся посты | `let` на верхнем уровне файла | `let` на верхнем уровне файла | приватное `#posts` в `PostStore` |
| Защита данных | нет | нет | приватные поля `#` |
| Перерисовка | вручную после каждого действия | вручную после каждого действия | автоматически по событию `'change'` |
| Валидация | в обработчике формы | в обработчике формы | в конструкторе `Post` (`throw`) |
| Работа с DOM | `createElement`, `textContent` | `$('<div>')`, `.text()`, `.prepend()` | `createElement` в `PostView`, только там |
| Клики по карточкам | обработчик на каждую кнопку | делегирование через `.on()` | делегирование + `closest()` в `PostView` |
| Глобальные переменные | есть | есть (`$`, `posts`) | нет, у модулей своя область видимости |
| Нужен сервер для запуска | нет | нет (нужен интернет) | **да** (из-за модулей) |
| Объём кода для такой задачи | минимальный | минимальный | заметно больше: 7 файлов |

Последняя строка важна: **ООП-версия объёмнее**. Для маленького приложения это честная плата. Мы платим строками за то, что код легко расширять, тестировать и понимать по частям. На 50 строках выгода не видна, на 5000 она огромна.

## Что стоит заметить в коде

- **`this` и `bind`** (`App.js`). Метод, переданный как колбэк, «отрывается» от объекта, и `this` внутри становится `undefined`. Лечится стрелочной функцией `(id) => this.#handleLike(id)` или привязкой `this.#handleLike.bind(this)`. В `App.js` показаны оба способа. Эта тема — классический вопрос на собеседовании.
- **Внедрение зависимостей** (`App.js`, `main.js`). `App` не создаёт store и view сам, а получает их готовыми. Поэтому в тестах можно подставить заглушки.
- **Отписка** (`EventEmitter.js`). `on()` возвращает функцию отписки. Тот же приём вы увидите в React: `useEffect` возвращает функцию очистки.
- **`getAll()` возвращает копию** (`PostStore.js`). Снаружи нельзя случайно испортить внутренний массив через `push`. Это первый шаг к идее **иммутабельности**, без которой не обходится React.
- **Модули вместо глобальных переменных** (`main.js`). Переменные модуля не попадают в `window`, и конфликтов имён больше нет.

## Чего всё ещё не хватает (и почему дальше фреймворки)

1. **Перерисовываем ВЕСЬ список** при каждом лайке (`replaceChildren`). На 10 постах незаметно, на 10 000 будет тормозить. Решение фреймворков: **Virtual DOM** (React, Vue) или компиляция (Svelte). Меняется только то, что действительно изменилось.
2. **Разметка живёт в JS** (`#createCard` собирает DOM по кусочку). Неудобно и плохо читается. Решение: **шаблоны** Vue (`<template>`) и **JSX** в React.
3. **Связывание руками.** `App` вручную подписывает всех на всех. Во Vue/React это делает сам фреймворк, а вы описываете только «что показать при таком состоянии» (**декларативный** подход вместо **императивного**).
4. **Компонентов нет в полном смысле.** `PostView` рисует весь список, а не отдельную карточку со своим состоянием. Компонент — это ровно «класс View + его разметка + его стили» в одной коробке.

Можно сказать, что в этой версии вы **написали маленький фреймворк своими руками**. Дальше станет видно, сколько работы Vue и React делают за нас.

## Задания для самопроверки

1. **Счётчик постов.** Добавьте в шапку текст «Постов: N». Не трогайте `PostView`: создайте маленький класс `CounterView` и подпишите его на `store.on('change', ...)` в `App`. Убедитесь, что на одно событие могут реагировать несколько слушателей.
2. **Сохранение в localStorage.** Подпишитесь на `'change'` и сохраняйте посты в `localStorage` (подсказка: у `Post` приватные поля, поэтому `JSON.stringify(post)` даст `{}`; добавьте в `Post` метод `toJSON()`). При старте загружайте посты обратно.
3. **Метод `unlike()`.** Добавьте в `Post` метод, уменьшающий лайки, но не ниже нуля. Правило должно жить в модели, а не в обработчике клика.
4. **Наследник.** Создайте `class PinnedPost extends Post` с полем `pinned = true` и сделайте так, чтобы закреплённые посты всегда были сверху списка.
5. **Сломайте `this`.** В `App.js` замените `this.#handleLike.bind(this)` на просто `this.#handleLike`, кликните лайк и прочитайте ошибку в консоли. Объясните её своими словами.
